# The Word keys tell the truth — r28 and r32 were stale keys, not lost headings

**Date:** 2026-09-03
**Predecessors:** `blind-test-2026-08-29-results.md` (the original claim),
`second-corpus-results.md` (the heading rule that made the keys stale),
`AGENTS.md` standing note "counts.headings on a Word row is a FIDELITY expectation".

## The claim being retracted

Two count disagreements stood on the record since the 2026-08-29 run: r28 (key 13,
delivered 12) and r32 (key 5, delivered 4), explained as "headings that do not survive
conversion". A later note in `AGENTS.md` said that explanation had never been verified.
This document verifies it, with the key author's own code path rather than another probe.

## Method

`author-real-keys.mjs`'s `readDocx` heading loop, run over the nine `r*` Word sources
under five variants of its rule, one per commit the rule has had plus the one this
change adds. Per-paragraph tables (index, style id, resolved level, text length, drawing
count — no text) identified the differing paragraph on every row that moved. The
delivered side is the last full run before this change (`2026-09-02T02-47-41-113Z`),
read with qpdf.

| variant | rule | commit |
|---|---|---|
| A | `HeadingN` style-name match, no `w:basedOn`, no empty skip | `5ad8352` (keys authored) |
| B | A + skip paragraphs with no `<w:t>` text | — |
| C | outline level (direct `w:outlineLvl`, or style level through `w:basedOn`), no empty skip | — |
| D | C + skip paragraphs with no `<w:t>` text | `56a08b2` ("today's rule") |
| E | C + skip paragraphs with no text AND no described drawing | this change |

## Per row, the paragraph that moved

- **r32** — paragraph 27 of 185: `Heading2`, zero text, one `<w:br w:type="page"/>`.
  Variant A counts it (it has the style); D and E do not (it says nothing). LibreOffice
  imports a lone page break as a paragraph property, so the flat ODF heading is empty
  and `removeEmptyHeadings` deletes it. Delivered 4 is correct.
- **r28** — paragraph 47 of 95: `Heading2`, zero text, one `<w:drawing>` whose
  `wp:docPr` carries a `descr`. Variant D calls it empty (no `<w:t>`); the product does
  not: the description lands in `<svg:desc>` inside the `<draw:frame>`, survives the
  tag-strip, and the export carries it as `/H2` over a `/Figure` with that `/Alt`.
  Delivered 12 is correct, and re-authoring under D would have set key 11 against
  delivered 12 — `invented-structure`, fatal at any weight, against a converter that had
  carried the author's own image. Variant E mirrors the product's test. (The other
  paragraphs A counts and D does not — 45, 54, 76 — are `Heading2` with nothing in them;
  paragraphs 11, 84–86 are a custom style based on `Heading2` that A cannot see.)
- **r23** — paragraph 22 of 254: `TOCHeading`, based on `Heading1`, 8 characters.
  **r30** — paragraph 4 of 191: `TOCHeading`, based on `Heading1`, 17 characters.
  Both are headings by OOXML's definition (outline level 1 through `w:basedOn`), and
  both are missing from the delivery: the delivered level sequences run
  `H1,H2,H3,…` and `H1,H1,H2,…` where the sources run `1,1,2,3,…` and `1,1,1,2,…`.
  `[V]` Converting r23 to flat ODF shows the mechanism: the flat ODF has 35 `<text:h>`
  and the TOC heading is the `<text:index-title>` of the table of contents, whose style
  `Contents_20_Heading` has `style:parent-style-name="Heading_20_1"` and
  `style:default-outline-level=""` — a `<text:p>`, not a `<text:h>`. **This is a real
  heading the conversion drops**, and the only one across the nine rows. It is recorded
  here as a product finding and appears in the scorecard as a non-fatal `counts-off` note
  on two probe rows. The key was not bent to match.
- **r33** — variant C counts 14 and D 13: one empty `Heading2` (no page break, no
  drawing). Deleted by the product, correctly.
- **r34** — 0 under every variant and 0 delivered. A raw qpdf read of the delivered PDF
  shows 18 elements typed `/H1` and `/H3`; the file's `/RoleMap` maps both to `/P`,
  because the source's custom paragraph styles are literally named "H1" and "H3" and
  carry no outline level. The product resolves the role map (`Inspect.standard()`) and
  reports 0; the ad-hoc probe that did not resolve it reported 18. The same instrument
  defect the PDF key author fixed at `56a08b2`, reproduced by a throwaway script — which
  is why the method above uses the author's code path.

## What changed

1. **The author's emptiness test mirrors the product's.** `author-real-keys.mjs` and
   `verify.mjs` (its twin, by the independence rule) count a heading paragraph that has
   `<w:t>` text OR a drawing (`wp:docPr` / `v:imagedata`) carrying a non-empty `descr` or
   `title`. The comment names r28 as the document that showed the two tests disagreeing.
2. **`corrections.json` gains `counts` corrections for r23, r28, r30 and r32**, kind
   `instrument-defect`, evidence naming the rule and both commits. Key files and hashes
   are unchanged. Re-running the cohort also re-read the `r` PDF rows under the current
   reading: no count moved; r13's `needs` gains the `4.1.2` the form-field rule added
   after the cohort's last corrections run (the product already voices it).
3. **Product: an undescribed image-only heading is demoted to a paragraph.** The plan
   predicted the old code would DELETE it (strip the tags, find nothing, drop the
   subtree). `[V]` It did not: a flat ODF embeds every image as base64 inside
   `office:binary-data`, the tag-strip left that payload standing as "text", and the
   first blind run of `w20` delivered the undescribed image-only heading as a heading —
   three against a key of two, `invented-structure`, fatal. So the defect was the
   opposite of the prediction: a heading announced over a figure with no name. Two
   things had to change, each measured before it was kept: `readableText` discounts
   `office:binary-data` before asking whether anything is left (and `firstHeading` uses
   it too, so an image-only first heading can never become a base64 title); and the
   demotion drops the STYLE NAME as well as the outline level, because a `<text:p>`
   still styled `Heading_20_2` was exported as `/H2` anyway — the style carries
   `style:default-outline-level="2"` and the importer reads a paragraph's level from its
   style when the tag does not say. Exporting the corrected flat ODF by hand gave
   `/H1 1, /H2 1, /Figure 2`. A described image-only heading stays a heading, as it
   always did. Tests in `flat-odf.test.ts` carry both shapes with the base64 in place.
4. **`w20-image-only-heading`** plants both shapes, `core`: a real H1, a `Heading2`
   whose only run is an undescribed drawing, a `Heading2` whose only run is a described
   drawing. Key: headings 2, figures 2, needs `1.1.1`. Three headings means the
   converter kept an empty heading; one means it dropped a described image; one figure
   means the demotion is still a deletion.

## Noticed, not done

- **The TOC heading loss is fixable in `flat-odf.ts`** — promote a
  `<text:index-title>`'s paragraph to `<text:h text:outline-level="1">` when its style
  descends from a heading style — but that is a transcription decision with its own
  evidence to gather (what Word's own PDF export does with it; whether every TOC title
  in the wild is outline-levelled), and it is out of this change's scope. r23 and r30
  carry it as open notes until then.
- `score.ts`'s asymmetry (more headings than the key is fatal at any weight) stays. It
  is why the key had to be right rather than the rule loosened.
